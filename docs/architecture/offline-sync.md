# Offline-first and synchronization

The app is designed to work without an internet connection. This page explains how data is stored locally and how it is synchronized with the backend when a network connection is available.

## Local storage — `LocalDatabase`

`lib/src/core/storage/local_database.dart` is a singleton that wraps `sqflite` (on mobile and desktop) and IndexedDB (on Web).

**Schema of the `local_patients` table:**

```sql
CREATE TABLE local_patients (
  patient_id    TEXT PRIMARY KEY, -- UUID v4 generated by the frontend
  device_uid    TEXT NOT NULL, -- NFC device UID
  patient_name  TEXT NOT NULL, -- Name to display in the UI (masked)
  record_json   TEXT NOT NULL, -- PatientFullRecord serialized as JSON (encrypted)
  is_synced     INTEGER NOT NULL DEFAULT 0, -- 0 = pending, 1 = synchronized
  sync_error    TEXT, -- Message of the last sync error
  sync_error_code INTEGER, -- HTTP status code of the last sync error
  created_at    TEXT NOT NULL, -- ISO 8601
  synced_at     TEXT, -- ISO 8601 — null until the first successful sync
  revision      INTEGER NOT NULL DEFAULT 0,
  owner_user_id TEXT,
  organization_id TEXT,
  pending_retired_reason TEXT
)
```

!!! note "Almacenamiento en Web"
sqflite is not available in Flutter Web. LocalDatabase uses IndexedDB
(backed by hwb_local_store) as its persistence layer on Web, not just a
development fallback — it is the production storage path for this
platform. Encryption keys on Web are kept in sessionStorage (so ciphertexts
in IndexedDB become unreadable upon closing the tab/session). Clinical payloads
(record_json) are encrypted with AES-256-GCM before being written, the index
patient_name column is masked (e.g. "Ana G.") rather than stored in full,
and the break-glass emergency log encrypts patient_name/user_id the same way.
See web/index.html's Content-Security-Policy for the defense-in-depth layer.

## Synchronization Engine — SyncEngine
lib/src/core/sync/sync_engine.dart implements the background synchronization cycle.

### Lifecycle

```dart
// Start connectivity monitoring
syncEngine.start();

// Stop (example, on logout)
syncEngine.stop();
```

### Synchronization Flow

```
Connectivity Detected (via connectivity_plus)
        │
        ▼
getUnsyncedRecords()   ← list local_patients WHERE is_synced = 0 AND owner_user_id = current_user
        │
        ▼ (for each record)
POST /api/v1/patients/sync
        │
   ┌────┴────┐
   │  201    │  → markSynced(patientId)   → removes the row from local storage
   │  4xx    │  → markSyncError(message)  → permanent error (holds/blocks row for review)
   │  5xx    │  → markSyncError(message)  → automatic retry
   │  401    │  → stop sync               → redirect to login
   └─────────┘
```

### Behavior by Error Code

| Code | Action |
|---|---|
| 201 | Marks as synchronized and deletes the row from local storage (markSynced)Marks as synchronized and deletes the row from local storage (markSynced) |
| 400 / 403 / 409 / 422 | Permanent error — holds row as blocked for review or user resolution |
| 401 | Stops synchronization entirely — token expired, requires re-login |
| 429 / 500 | Keeps `is_synced = 0` for automatic retry |
| 503 `sync_in_progress` | Another request was creating the same new patient (a retry racing the first attempt). Kept pending, not blocked, and retried no sooner than `Retry-After` (5 s) or the backoff, whichever is longer; the retry merges into the record the other request created. The queue shows it as pending |
| Timeout | Keeps `is_synced = 0` for automatic retry |

Transient failures (408, 429, 5xx, network) schedule the next attempt whether
they come from a background cycle or from **Sync now** on one record.

```dart
syncEngine.onRecordSynced = (String patientId, bool success, String? error) {

syncEngine.savedRecords.listen((RecordSyncResult result) {

```

### Record versions and `conflicts`

`/scan` and `/search` return the server's `recordVersion`. The app keeps it on
`PatientFullRecord.recordVersion` and sends it back to `/sync` as
`baseVersion`: the version its copy was based on. `toJson()` writes it under
that name, and `fromJson()` reads it back from it, so the version survives the
local queue and the guardian device.

A `/sync` that the server accepts (`201`) answers with `record_version` (the
version after this sync) and `conflicts` (the parts it kept as it had them, for
example `stale_payload_base_version` when `baseVersion` was older than its
own). The engine announces every saved record on `SyncEngine.savedRecords`:

- The open profile adopts the new version, so its next edit is not taken for
  an old copy. An edit made while the sync was in flight is saved again on top
  of the new version.
- When `conflicts` is not empty, the engine marks both chips for rewriting and
  stores a notice (`sync_notices` table, one per patient, masked name) that the
  sync queue lists until the user dismisses it. If the server sends its merged
  record back (`record`), the profile shows it; otherwise the copy keeps its
  old version, so anything edited next is merged rather than applied over the
  server's.
- If only the FHIR delivery failed, the row stays queued to re-send the bundles
  and is moved onto the new version, since it holds exactly what was saved.

### Records of another user

Every row carries `owner_user_id`. The engine, the sync queue and the home counts
select the signed-in user's rows (and ownerless rows, which the first sync
adopts). Another user's pending rows stay on the device, encrypted and unlisted,
until that user signs in again; the queue only shows how many there are.
Signing in as someone else no longer blocks or offers to discard them.

`AuthRepository.clearSession()` deletes only the session's keys on a phone. On
Android `flutter_secure_storage` keeps every key in one file, the local
database's AES keys included, so `deleteAll()` would leave the pending rows
unreadable after a restart. On the web it still deletes everything, and logout
wipes the local PHI.

### Retired devices

A lost, damaged or replaced patient or guardian device still holds its data, and
offline the reader opens a record from the devices alone. Online the server
answers `410 device_retired`; offline the reader checks a local list first.

- **The list.** `GET /api/v1/patients/retired-devices` returns, for every retired
  device, `sha256("hwb-retired-device:v1:" + UID)` with the UID reduced to its hex
  digits in upper case (`retiredDeviceHash` in
  `lib/src/core/nfc/retired_device_hash.dart`). The phone keeps hashes, not UIDs.
  The test vectors are shared with the backend
  (`tests/contract/fixtures/retired_device_hashes.json` there).
- **Download.** Each `syncAll()` cycle, once the backend is reachable, asks for
  what was retired since the last `server_time` and stores it with the new one
  (tables `retired_devices` and `retired_devices_cursor`, schema v12). A failure
  keeps the previous list. `clearAll()` keeps it: it belongs to no user.
- **Learned on the spot.** A `410 device_retired` from `/scan`, and the old UIDs
  of a reassignment made on this phone, go into the list right away.
- **Offline read.** A retired patient device is refused with the same message as
  online, without the guardian step or emergency access. A retired guardian device
  is refused, and the guardian step stays open for the new one.
- **Never downloaded.** Until the first list arrives, a record still opens
  offline, with a warning that the device could not be checked.
- **Storage errors** answer "not retired": a local failure never blocks care.

## Scrubbing of Clinical Data

Once a record is successfully synchronized with the backend (HTTP 201), the app removes the entry from local storage (markSynced deletes the row in local_patients).

This protects patient privacy in case of device loss or theft.

## Connectivity

SyncEngine subscribes directly to network change events via connectivity_plus (WiFi, mobile data) and probes backend reachability using Reachability.probe(). Upon regaining connection to a valid server, it automatically triggers syncAll().
